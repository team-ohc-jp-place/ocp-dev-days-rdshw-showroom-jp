= コミットへの署名
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

各コミットには変更の記録が残りますが、その記録が本物だとどう確認するのでしょうか。作成者は `git config` コマンド 1 つで偽装できます。リポジトリへのアクセス権が侵害されたり、SSH 鍵や GPG 鍵が紛失、盗難、共有されたりする可能性もあります。従来のコード署名では、開発者自身が長期利用する鍵ペアを管理、更新、保護する必要があり、それが十分に行われないこともあります。

この環境では、クラスタ基盤としてデプロイされた **Red Hat Trusted Artifact Signer (RHTAS)** による **Sigstore キーレス署名** を使い、署名を鍵ペアではなく開発者の *ID* に結び付けます。コミットへの署名時に組織の ID プロバイダ (ここでは Keycloak SSO) で認証すると、RHTAS の認証局である Fulcio が短期間有効な証明書を発行します。署名は Rekor の透明性ログに記録され、証明書は数分で失効します。管理、紛失、更新の対象となる長期利用の鍵はありません。

このセクションでは、先ほどの脆弱性修正をコミットし、自分の ID で署名します。

[#section-1]
== Section 1: コミットと署名

[#_exercise_1_commit_your_changes]
=== 演習 1: 変更をコミットする

. Dev Spaces で **Source Control** パネルを開きます。左サイドバーのブランチアイコン、または `Ctrl+Shift+G` を使います。

. 変更一覧に、修正した `pom.xml` が表示されていることを確認します。

. 変更内容が分かるコミットメッセージを入力します。
+
[source,role="copypaste"]
----
Cleared most of the application vulnerabilities
----

. **Commit** ボタン (チェックマークのアイコン) をクリックします。
+
image::m02-devspaces-commit.png[Source Control で変更をコミット,link=self,window=blank,width=700]

. 変更をステージしていないため、**Yes** をクリックして直接コミットします。
+
image::m02-devspaces-stage-commit.png[ステージとコミットの確認,link=self,window=blank,width=400]

. VSCode から Keycloak SSO の Web サイトを開くよう求められたら、**Open** をクリックします。
+
image::m02-devspaces-open-keycloak.png[VS Code の Keycloak SSO を開く確認,link=self,window=blank,width=700]
+
ブラウザのタブまたはポップアップが開き、成功コードが表示されます。これが Sigstore の OIDC ログインフローです。

. コピーアイコンをクリックして成功コードをコピーします。
+
image::m02-gitsign-login-prompt.png[Keycloak SSO の成功コード,link=self,window=blank,width=400]

. **gitsign login** のターミナルに貼り付け、**Return** を押します。
+
NOTE: これは Linux のターミナルです。ブラウザや設定によっては、貼り付けに kbd:[Ctrl+V] ではなく kbd:[Ctrl+Shift+V] を使う必要があります。
+
image::m02-gitsign-code-paste.png[gitsign ターミナルへの検証コードの貼り付け,link=self,window=blank,width=700]
+
これで、コミットに自分の ID に基づく署名が付与されました。

. **Sync Changes** (またはプッシュアイコン) をクリックし、署名したコミットを GitLab にプッシュします。
+
image::m02-devspaces-sync-changes.png[Source Control の Sync Changes ボタン,link=self,window=blank,width=300]

. Developer Hub のサンドボックスコンポーネントに戻り、**View Source** をクリックします。 {gitlab_url}[{gitlab_url}^] から移動することもできます。コミットを探し、その横に署名バッジ (unverified) があることを確認します。
+
image::m02-rhdh-view-source.png[サンドボックスコンポーネントの View Source リンク,link=self,window=blank,width=700]
+
バッジをクリックして証明書の詳細を確認します。**Certificate Issuer** は `CN=CISO-office,O=Parasol` です。**Certificate Subject** が空なのは、署名者の ID を Subject Alternative Name に格納する Sigstore / RHTAS の署名構造を、GitLab が現時点で理解できないためです。また、公開鍵は透明性データベースに格納され、短命な証明書ごとに変わるため、GitLab は現時点では Sigstore の署名自体も検証できません。
+
image::m02-gitlab-signed-commit.png[GitLab の署名付きコミットと証明書の詳細,link=self,window=blank,width=700]

[#_why_is_this_important]
=== なぜ重要なのでしょうか

* **説明責任**: コミットが、Git の設定にある名前だけでなく、検証済みの ID に暗号学的に結び付きます
* **改ざんの検知**: 署名されたコミットを変更すると、署名の検証が失敗します
* **鍵管理が不要**: 開発者が署名鍵を生成、保存、更新する必要がありません
* **透明性**: 各署名が公開の透明性ログ (Rekor) に記録され、監査可能な履歴が残ります
* **パイプラインによる強制**: 後続の段階で、ビルド前にコミットが署名済みか検証されます

[#_how_was_it_done]
=== 実装の仕組み

演習を読みやすくするため、実装の詳細は以下にまとめています。展開して確認してください。

.**実装の詳細を表示**
[%collapsible]
====
Git は、署名プログラムとして **gitsign** を使うよう設定されています。Dev Spaces のワークスペース起動時に、devfile の `postStart` コマンドで自動設定されます。

[source,bash]
----
git config --global gpg.format x509
git config --global gpg.x509.program gitsign
git config --global commit.gpgsign true
git config --global gitsign.fulcio "https://fulcio-server-trusted-artifact-signer.{subdomain}"
git config --global gitsign.rekor "https://rekor-server-trusted-artifact-signer.{subdomain}"
git config --global gitsign.issuer "https://sso.{subdomain}/realms/sso"
----

**Sigstore キーレス署名のフロー** は以下のとおりです。

. 開発者がコミットを開始します
. Gitsign が認証のため OIDC プロバイダ (Keycloak) にリダイレクトします
. 認証後、gitsign が認証局の **Fulcio** に短命な証明書を要求します
. Fulcio が、開発者のメールアドレスを Subject Alternative Name に含む証明書を発行します
. Gitsign がこの証明書を使ってコミットに署名します
. 監査できるよう、署名が透明性ログの **Rekor** に記録されます
. 証明書は数分で失効しますが、Rekor の記録により、署名時点で有効だったことを証明できます

Dev Spaces はローカルブラウザのないコンテナ内で動作するため、**gitsign-credential-cache** デーモンが検証コードを表示し、開発者がターミナルに貼り付けることで OIDC フローを処理します。ローカルの IDE では、gitsign がブラウザを直接開きます。
====

=== 確認

* コミットを GitLab にプッシュした
* GitLab に署名バッジが表示されることを確認した
