= Namespace の保護
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

セキュアなパイプラインは、正しく署名、スキャン、承認されたイメージだけが *ビルド* されるようにします。しかし、誰かがパイプラインを迂回し、`oc` や `kubectl` で未署名のイメージを直接デプロイすることは、どう防ぐのでしょうか。ここで **Sigstore Policy Controller** を使用します。

Policy Controller は、Pod 作成要求を受け取り、実行を許可する *前に* コンテナイメージの署名とアテステーションを検証する Kubernetes アドミッションコントローラです。Parasol のセキュアな本番用 Namespace では、以下の 3 つのポリシーを満たす必要があります。

* イメージが Tekton Chains または Red Hat によって **署名** されていること
* SLSA アテステーションに **署名付きコミットの証拠** があること
* **署名付きのリリース承認** アテステーションがあること

[#section-1]
== Section 1: ポリシーによる制御を試す

[#_exercise_1_try_to_deploy_an_unsigned_image]
=== 演習 1: 未署名のイメージのデプロイを試す

. Dev Spaces を開きます。ターミナルを使うだけなので、どのワークスペースでも構いません。**New Terminal** をクリックします。
+
image::m02-devspaces-new-terminal.png[Dev Spaces でターミナルを新規作成,link=self,window=blank,width=700]

. ターミナルで、未署名のイメージをセキュアな本番用 Namespace にデプロイしてみます。
+
[source,bash,subs="attributes",role="copypaste"]
----
oc create deployment test-unsigned --image=docker.io/library/nginx:latest -n {user}-secured-prod
----

. アドミッション Webhook がデプロイを **拒否** します。出力が長いため、違反したポリシーだけに絞り込みます。
+
[source,bash,subs="attributes",role="copypaste"]
----
oc create deployment test-unsigned --image=docker.io/library/nginx:latest -n {user}-secured-prod 2>&1 | grep "failed policy:"
----
+
----
failed policy: parasol-image-signature-required
failed policy: parasol-signed-commit-required
failed policy: parasol-release-approval-required
----
+
image::m02-policy-controller-reject-unsigned.png[未署名イメージに対して全 3 ポリシーが失敗した出力,link=self,window=blank,width=700]

3 つすべてのポリシーに違反しました。nginx イメージは Chains や Red Hat の署名、SLSA アテステーション、承認のいずれも持っていません。

[#_exercise_2_try_to_deploy_a_signed_but_unapproved_image]
=== 演習 2: 署名済みだが未承認のイメージのデプロイを試す

. MR チェック時に作成した、一時的なイメージをデプロイしてみます。Chains による署名はありますが、未承認です。
+
[source,bash,subs="attributes",role="copypaste"]
----
oc create deployment test-no-approval --image=quay.{subdomain}/{user}/parasol-insurance-secured:mr-1 -n {user}-secured-prod
----

. このデプロイも **拒否** されます。再び出力を絞り込みます。
+
[source,bash,subs="attributes",role="copypaste"]
----
oc create deployment test-no-approval --image=quay.{subdomain}/{user}/parasol-insurance-secured:mr-1 -n {user}-secured-prod 2>&1 | grep "failed policy:"
----
+
----
failed policy: parasol-release-approval-required
----
+
image::m02-policy-controller-reject-unapproved.png[署名済み・未承認のイメージに対して承認だけが失敗した出力,link=self,window=blank,width=700]
+
Chains の署名があるためイメージ署名のチェックには合格しますが、この MR チェック用イメージは本番向けに承認されていないため、リリース承認ポリシーに違反します。

[#_exercise_3_verify_the_legitimate_deployment_works]
=== 演習 3: 正規のデプロイが動作することを確認する

. tag-promote パイプラインを通じてデプロイした本番環境が動作していることを確認します。
+
[source,bash,subs="attributes",role="copypaste"]
----
oc get pods -n {user}-secured-prod
----
+
`parasol-insurance` と `parasol-db` の Pod が正常に実行されているはずです。これらのイメージは 3 つすべてのポリシーに合格しています。

. 失敗したテスト用のデプロイを削除します。
+
[source,bash,subs="attributes",role="copypaste"]
----
oc delete deployment test-unsigned test-no-approval -n {user}-secured-prod 2>/dev/null
----

[#_why_is_this_important]
=== なぜ重要なのでしょうか

パイプラインは重要なセキュリティ対策ですが、Namespace へのアクセス権があれば `oc apply` で任意のイメージをデプロイし、迂回することができます。Policy Controller はこの隙間を埋めます。

* パイプラインより下位の **Kubernetes のアドミッション層** で動作します
* ビルド時ではなく **デプロイ時** に署名とアテステーションを検証します
* ArgoCD、`oc`、Helm、手書きの YAML など、起動方法にかかわらず **すべての Pod 作成** に適用されます
* **多層防御** を実現します。パイプラインが侵害されても、未署名のイメージや、必須のアテステーションおよびその値が欠けたイメージは実行できません

[#_how_was_it_done]
=== 実装の仕組み

演習を読みやすくするため、実装の詳細は以下にまとめています。展開して確認してください。

.**実装の詳細を表示**
[%collapsible]
====
**Sigstore Policy Controller** は RHTAS Operator でインストールし、`ClusterImagePolicy` カスタムリソースで設定します。

`{user}-secured-prod` Namespace にデプロイされるすべてのイメージに、以下の 3 つのポリシーが適用されます。

[cols="1,2",options="header"]
|===
| ポリシー | チェック内容

| `parasol-image-signature-required`
| Tekton Chains (Fulcio / Rekor によるキーレス署名) または Red Hat (release3 公開鍵) の署名があること

| `parasol-signed-commit-required`
| SLSA 来歴のアテステーションに、`SIGNATURE_STATUS: SIGNED` の `verify-commit-signature` タスクが含まれること

| `parasol-release-approval-required`
| `*@demo.redhat.com` の ID で署名され、`release.approved: true` を持つ独自アテステーション (`parasol-insurance.com/releases/v1`) があること
|===

各ポリシーには **2 つの認証元** があり、OR 条件で評価します。

* **Tekton Chains / ユーザー ID** -- クラスタの Sigstore 基盤 (Fulcio + Rekor) の署名を検証します
* **Red Hat の署名** -- Red Hat release3 公開鍵で署名を検証し、PostgreSQL などの Red Hat ベースイメージが Chains の署名なしでも通過できるようにします

以下のラベルで、Namespace にポリシーの強制適用を有効化します。

[source,yaml]
----
metadata:
  labels:
    policy.rhtas.com/include: "true"
----

このラベルを持つ Namespace だけがポリシーの対象です。ビルド用、サンドボックス用、本番以外の Namespace にはラベルが付いておらず、影響を受けません。
====

[#_verify]
=== 確認

ここまでで、以下を確認できているはずです。

* 未署名のイメージをデプロイし、3 つのポリシーすべてで拒否されることを確認した
* 署名済みで未承認のイメージをデプロイし、承認ポリシーで拒否されることを確認した
* 正規の本番デプロイが実行されていることを確認した
* Policy Controller がパイプラインを補完する多層防御を提供する仕組みを理解した

'''

[#_congratulations]
== お疲れさまでした

セキュアなソフトウェアサプライチェーンのモジュールが完了しました。各段階のセキュリティ対策とともに、脆弱性の検出から本番デプロイまでの一連の流れを体験しました。

[cols="1,2",options="header"]
|===
| 段階 | セキュリティ対策

| **コード** | Red Hat Dependency Analytics が IDE 内で脆弱性を特定します
| **コミット** | Sigstore のキーレス署名が各コミットを検証済み ID に結び付けます
| **サンドボックスのビルド** | ACS のスキャンとポリシーチェックが早期に情報を提供します
| **マージリクエスト** | 署名検証を強制し、ACS ポリシー違反があるとマージを阻止します
| **マージ後のビルド** | Tekton Chains がイメージに署名し、SLSA アテステーションを生成します
| **タグによる昇格** | Conforma がアテステーションのチェーン全体を検証し、SBOM を TPA にアップロードします
| **承認** | 本番反映前に、人による署名付きの認可を要求します
| **デプロイ** | Policy Controller がアドミッション時に署名とアテステーションを検証します
|===

各証拠は暗号学的に署名され、透明性ログに保存され、独立して検証できます。これが **SLSA Level 3** に準拠したソフトウェアサプライチェーンです。
