= 脆弱性への早期対処
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

従来のセキュリティ対策では、パイプラインの最後、場合によってはデプロイ後にスキャンを行います。その段階で脆弱性が見つかると、手戻りや遅延、緊急パッチが必要です。よりよい方法は **シフトレフト** です。コードを書いている段階から、できるだけ早く脆弱性を特定して修正できるツールを開発者に提供します。

このセクションでは、セキュアな開発環境を準備し、Red Hat Dependency Analytics でアプリケーションの依存関係の脆弱性を見つけて修正します。コミットをプッシュする前に対処します。

NOTE: このモジュールでは、Red Hat Developer Hub の全機能や日常の開発支援は扱いません。開発者エクスペリエンスについては xref:module-01/00-intro.adoc[Module 1: 開発者エクスペリエンス] を参照してください。ここでは、開発プロセスに追加されたセキュリティのガードレールに焦点を当てます。

== Section 2: Red Hat Dependency Analytics

Red Hat Dependency Analytics (RHDA) は、アプリケーションの依存関係をリアルタイムで分析する IDE 拡張機能です。既知の脆弱性を特定して修正を提案し、Red Hat の Trusted Profile Analyzer (TPA) と連携して詳細な脆弱性データを提供します。公開データベースにはない Lightwell のバックポートによる修正情報も含まれます。

[#_exercise_2_fix_framework_vulnerabilities]
=== 演習 2: フレームワークの脆弱性を修正する

. `pom.xml` に戻り、脆弱な依存関係の赤い波線を確認します。

. 下線付きの依存関係にカーソルを合わせ、電球アイコンが表示されたら **Quick Fix** をクリックします。
+
image::m02-rhda-quickfix-hover.png[脆弱な依存関係の Quick Fix 表示,link=self,window=blank,width=500]
+
image::m02-rhda-quickfix.png[脆弱な依存関係への Quick Fix の提案,link=self,window=blank,width=500]
+
IMPORTANT: Quarkus などのフレームワークでは、個別の依存関係だけにクイックフィックスを適用すると、フレームワーク内でバージョンの不整合が起こることがあります。以下のように、フレームワーク全体のバージョンを更新してください。

. `pom.xml` で `quarkus.platform.version` を探し、新しいバージョンに更新します。原文作成時点で、**直接依存の脆弱性** を修正する最新バージョンは 3.20.5 でした。
+
[source,xml,role="copypaste"]
----
<quarkus.platform.version>3.20.5</quarkus.platform.version>
----

. VSCode がファイルを自動保存すると、RHDA が再分析します。レポートで、フレームワークの直接依存の脆弱性がなくなり、その他も減っていることを確認します。

. **直接依存の脆弱性** が見つからない場合、警告は表示されません。ステータスバーの盾アイコンか右上の円グラフアイコンからレポートを開けます。
+
image::m02-rhda-shield-button.png[RHDA レポートを開くステータスバーの盾アイコン,link=self,window=blank,width=700]

. `quarkus-rest` の依存関係の波線も消えたことを確認します。



. 続いて、フレームワークを最新バージョンに更新します。
+
[source,xml,role="copypaste"]
----
<quarkus.platform.version>3.40.1</quarkus.platform.version>
----

. 自動保存後、分析の完了を待ちます。脆弱性は数件程度まで減るはずです。
+
image::m02-rhda-report-after-fix.png[フレームワークの更新後の RHDA レポート,link=self,window=blank,width=700]

[#_why_is_this_important]
=== なぜ重要なのでしょうか

コードを書いている最も早い段階で脆弱性情報を提供すると、開発者は根拠を持って以下の判断ができます。

* パイプラインを実行する前にフレームワークのバージョンを更新する
* Lightwell のバックポート (依存関係のバージョンを変えずに置き換えられる修正) と、アップストリームによる修正 (互換性に影響する可能性のあるバージョンアップ) の違いを理解する
* 重大度や悪用可能性に基づいて修正の優先順位を決める

これが **シフトレフトセキュリティ** の本質です。数時間後の CI/CD の失敗で問題に気付くのではなく、開発者が早い段階で情報と対処の手段を得られます。

[#_how_was_it_done]
=== 実装の仕組み

演習を読みやすくするため、実装の詳細は以下にまとめています。展開して確認してください。

.**実装の詳細を表示**
[%collapsible]
====
Red Hat Dependency Analytics は、**{tpa_url}[Trusted Profile Analyzer (TPA)^]** というバックエンドサービスに問い合わせます。この環境では TPA がクラスタにデプロイされ、複数の情報源から脆弱性データを取り込んでいます。

* **CVE List v5** -- 業界標準の脆弱性データベース
* **GitHub Security Advisories (GHSA)** -- オープンソースコミュニティからの脆弱性レポート
* **Lightwell** -- 公開データベースにないバックポートや置き換え用の修正版を提供する、Red Hat の商用脆弱性インテリジェンスサービス

RHDA は VS Code (および IntelliJ) の拡張機能です。ワークスペースの設定で、このクラスタの TPA インスタンスを使うよう構成されています。

[source,json]
----
"redHatDependencyAnalytics.backendUrl": "https://rhda.{subdomain}"
----

`pom.xml`、`package.json`、`go.mod` などを開くと、RHDA が依存関係ツリーをバックエンドに送信します。バックエンドは取り込み済みの脆弱性データと照合し、Lightwell による修正情報を含む結果を返します。

Dependency Analytics のレポートから Trusted Profile Analyzer を直接開くこともできます。

image::m02-rhda-tpa-link.png[RHDA から TPA を開く Take me there,link=self,window=blank,width=700]
====

[#_verify_2]
=== 確認

この時点で、以下ができるようになっているはずです:

* pom.xml を開き、RHDA が脆弱な依存関係を強調表示することを確認した
* 重大度別の内訳と修正方法を示す RHDA レポートを開いた
* フレームワークのバージョンを更新し、脆弱性の減少を確認した

'''
