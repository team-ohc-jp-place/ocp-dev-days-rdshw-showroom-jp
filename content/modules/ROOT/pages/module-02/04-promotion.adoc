include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

サンドボックスのイメージでは、脆弱性の対処、ベースイメージの強化、コミットへの署名が完了しました。ここから、マージリクエストのチェック、マージ後のビルド、タグによる本番昇格という、セキュアなパイプラインの各段階に変更を進めます。

サンドボックスとは異なり、これらのパイプラインはセキュリティポリシーを **強制適用** します。未署名のコミット、ポリシー違反、承認の欠如があると昇格を阻止します。

== Section 1: マージリクエスト

[#_exercise_1_create_a_merge_request]
=== 演習 1: マージリクエストを作成する

. GitLab を開き、`parasol-insurance-secured` リポジトリのサンドボックスブランチに移動します。
+
Developer Hub のサンドボックスコンポーネントで **View Source** をクリックすると、素早く移動できます。
+
image::m02-rhdh-sandbox-view-source.png[サンドボックスコンポーネントの View Source,link=self,window=blank,width=700]

. **Create merge request** をクリックします。**Merge Requests** → **New merge request** からも作成できます。
+
image::m02-gitlab-create-mr.png[GitLab の Create merge request ボタン,link=self,window=blank,width=700]

. ソースにサンドボックスのブランチ、ターゲットに `main` を指定します。
+
image::m02-gitlab-new-mr-form.png[ソース・ターゲットブランチを指定する MR のフォーム,link=self,window=blank,width=700]

. 変更内容が分かるタイトルを入力します。
+
[source,role="copypaste"]
----
Sec-fix done, security posture improved
----
+
「Description」を削除し、**Create merge request** をクリックします。

[#_exercise_2_watch_the_mr_check_pipeline]
=== 演習 2: MR チェックパイプラインを確認する

. マージリクエストの作成後、チェック用のパイプラインが自動起動します。preprod 向けにビルドできるか、チェックに合格するか、組織の基準に準拠するかを確認します。失敗すると変更をマージできません。これが **マージリクエストのチェックパイプライン** で、サンドボックスではなく Parasol のセキュアなビルド用 Namespace で実行されます。
+
image::m02-gitlab-mr-pipeline-running.png[MR チェック実行中のマージの保留,link=self,window=blank,width=700]

. GitLab のパイプライン画面でタスクをクリックすると、Developer Hub に MR Check のパイプライン実行が開きます。
+
image::m02-gitlab-mr-pipeline-jobs.png[GitLab MR のコミット検証と ACS のタスク,link=self,window=blank,width=700]

. 対象のコンポーネントは、サンドボックスではなく `Parasol Insurance (Secured)` であることを確認します。
+
image::m02-rhdh-mr-check-pipeline.png[Developer Hub のセキュアな Parasol の MR チェック,link=self,window=blank,width=700]

. MR チェックパイプラインは以下を行います。
* **コミット署名の検証** -- `ENFORCE=true` のため、未署名のコミットは **パイプラインを失敗** させます
* MR ブランチから **イメージをビルド** します
* ACS ポリシーに基づいてイメージを **スキャン、チェック** します
* GitLab にコミットのステータスと詳細な MR コメントとして **結果を報告** します

. パイプラインの完了を待ちます。

. GitLab のマージリクエストのページに戻ります。
* 「Merge」ボタンが有効になりますが、マージする前に結果を確認します
* Activity の最新の **🔀 Merge Request Check Results** コメントまでスクロールし、署名状態、ACS ポリシーの結果、脆弱性件数を確認します
* 今回は事前チェックが成功しているため、結果の確認のみです。失敗時には、原因と修正方法の調査に役立ちます
+
image::m02-gitlab-mr-ready-to-merge.png[パイプライン成功後のマージ可能な MR,link=self,window=blank,width=700]
+
image::m02-gitlab-mr-results.png[署名と ACS の検証を示す MR チェック結果,link=self,window=blank,width=700]

[#_exercise_3_merge_the_request]
=== 演習 3: リクエストをマージする

. すべてのチェックに合格すると、**Merge** ボタンが有効になります。
+
NOTE: 未署名のコミットなどでパイプラインが失敗すると、マージは阻止されます。GitLab の `onlyMergeWhenPipelineSucceeds` 設定で制御しています。

. **Merge** をクリックします。
+
これにより **マージ後のビルドパイプライン** が起動します。`main` から **__最終イメージ__** がビルドされ、Tekton Chains による署名とアテステーションが付与されて Quay に保存され、preprod 環境にデプロイされます。
+
image::m02-rhdh-post-merge-pipeline.png[Developer Hub のマージ後のビルド,link=self,window=blank,width=700]

'''

== Section 2: 本番環境への昇格

マージ後のビルドで、`main` から署名付きイメージが作成されました。本番環境に昇格するには **Git タグ** を作成し、tag-promote パイプラインを起動します。

+
image::m02-gitlab-create-tag.png[GitLab でタグを作成,link=self,window=blank,width=700]

[#_exercise_2_watch_the_tag_promote_pipeline]
=== 演習 2: tag-promote パイプラインを確認する

* レジストリからイメージの SHA を取得します

* **SBOM** を生成して TPA にアップロードします
* バージョンタグを付けたイメージをレジストリにコピーします
* GitOps マニフェストリポジトリに、本番デプロイを更新する **マージリクエスト** を作成します

. Developer Hub で **Parasol Insurance (Secured)** コンポーネントを開き、**CI** タブをクリックします。
+
`parasol-insurance-secured-tag-promote` のパイプライン実行を探します。

+
image::m02-rhdh-tag-promote-view-output.png[失敗した tag-promote の View output ボタン,link=self,window=blank,width=700]

image::m02-rhdh-ec-validation-failed.png[承認ルールが失敗した Enterprise Contract 検証,link=self,window=blank,width=700]

[#_exercise_3_understand_the_conforma_policy_violation]
=== 演習 3: Conforma ポリシー違反を理解する

. **Conforma (ec)** は、イメージの署名付きアテステーションをポリシー群に照らして検証します。以下の結果を確認してください。
* ✅ **Image signature check** -- Tekton Chains による署名があります
* ✅ **Attestation signature check** -- アテステーションに有効な署名があります
* ✅ **Commit must be signed** -- SLSA アテステーションが、コミットの署名を証明しています
* ✅ **ACS checks passed** -- イメージスキャンとポリシーチェックの結果がアテステーションに含まれています
* ✅ **SonarQube quality gate** -- コード品質の指標がアテステーションに含まれています
* ❌ **Parasol Release Approved** -- リリース承認のアテステーションがありません
+


. イメージのリリースが未承認のため、パイプラインは正しく昇格を阻止しました。イメージには **リリース承認の署名付きアテステーション** が付与されていません。

[#_why_is_this_important]
=== なぜ重要なのでしょうか

本番環境のイメージには、完全な **SLSA 来歴のチェーン** が付与されています。

* **署名付きコミット** -- 検証済みの開発者 ID に追跡できます
* **SLSA アテステーション** -- ビルドパイプラインの実行、実行されたタスク、その結果を証明します
* **ACS スキャン結果** -- 脆弱性評価の結果がアテステーションに含まれます
* **SonarQube の結果** -- コード品質の指標がアテステーションに含まれます
* **署名付き承認** -- リリースに対する人の明示的な認可を示します
* **SBOM** -- イメージの全コンポーネント一覧が TPA に保存され、継続的な脆弱性照合に使われます

形式的なチェックではなく、各証拠が暗号学的に署名され、個別に検証できます。

[#_how_was_it_done]
=== 実装の仕組み

演習を読みやすくするため、実装の詳細は以下にまとめています。展開して確認してください。

.**実装の詳細を表示**
[%collapsible]
====
**Tekton Chains** は Sigstore のキーレス署名で、パイプラインの成果物に自動で署名します。

* パイプラインの実行後、Chains がパイプラインの ServiceAccount の ID で **Fulcio** に短命な証明書を要求します
* すべてのタスク結果を含む **SLSA 来歴のアテステーション** を作成します
* アテステーションと署名は透明性ログの **Rekor** に記録され、レジストリ内のイメージにも付与されます

**Conforma (Enterprise Contract)** は、 {gitlab_url}/parasol/conforma-policies[GitLab の `conforma-policies` リポジトリ^] にある Rego ポリシー群でアテステーションを検証します。`parasol-software-supply-chain` バンドルは以下をチェックします。

* 必須タスク (verify-commit-signature、acs-image-scan、acs-image-check、sonar-scan) が実行されたこと
* コミットの署名状態が `SIGNED` であり、未署名やボットのコミットでないこと
* ACS ポリシーチェックに合格したこと
* SonarQube 品質ゲートに合格したこと
* イメージに署名付きのリリース承認アテステーションがあること

image::m02-gitlab-conforma-policies.png[GitLab の Conforma ポリシーリポジトリ,link=self,window=blank,width=700]

**承認のアテステーション** は、述語の型が `https://parasol-insurance.com/releases/v1` の独自の in-toto アテステーションです。Fulcio を通じて承認者の ID で署名し、Chains のアテステーションとともにイメージに付与します。

本番環境のイメージに付与された署名付きアテステーションを調べるには、Developer Hub の **Parasol Insurance (Secured)** コンポーネントから **Release Approval** アプリケーションに戻ります。

image::m02-rhdh-release-approval-link.png[セキュアな Parasol コンポーネントの Release Approval,link=self,window=blank,width=400]

タグをクリックし、そのイメージの署名付きアテステーションを確認します。

image::m02-approval-inspect-attestations.png[タグからアテステーションを確認,link=self,window=blank,width=500]

ここでは、独自アテステーションの署名者 ID と、Tekton Chains が自動生成して署名したアテステーションを確認できます。

image::m02-approval-attestation-details.png[署名者 ID とリリース承認および SLSA 来歴の詳細,link=self,window=blank,width=700]

**Attestation Detail** では、イメージとともに保存されたアテステーションを確認できます。

image::m02-approval-attestation-json.png[predicate と subject を含む in-toto のアテステーション詳細,link=self,window=blank,width=700]

**SBOM** は **syft** で生成し、開発者とバージョンタグを示すラベル付きで TPA にアップロードします。TPA は取り込んだ脆弱性データと SBOM を継続的に照合し、デプロイ済みイメージのセキュリティ状態を可視化します。
====

[#_verify]
=== 確認

ここまでで、以下を確認できているはずです。

* 署名付きコミットの MR をマージし、マージ後のビルドの成功を確認した
* タグを作成し、承認がないため tag-promote パイプラインが失敗することを確認した
* リリースを承認し、Conforma の検証の成功を確認した
* 完全な SLSA 来歴のチェーンを持つ本番デプロイを確認した

'''
