[id='lab3-service-interconnect']
== データベース接続の有効化

連携フローにはデータベースへのアクセスが必要ですが、まだ接続できません。理由を確認し、接続を有効にしましょう。

NOTE: この演習では理解しやすいように 1 つのクラスタを使いますが、Service Interconnect はネットワークポリシーだけでは扱えない、クラスタ、地域、クラウドをまたぐ複数拠点のメッシュにも対応します。最後に、より広い利用場面の例を紹介します。

{empty} +

[#_why_cant_you_reach_the_database]
=== なぜデータベースに接続できないのでしょうか

バックエンドデータベースは、厳しいネットワークポリシーで隔離された Namespace (*shared-database*) にあります。他の Namespace からの直接アクセスは許可されていません。

* `"SELECT count(*) FROM policies"` — データベースのレコード数を取得します
====
--

自分の Namespace から直接アクセスできないため、接続はタイムアウトします。

[#_bridging_namespaces_with_service_interconnect]
=== Service Interconnect で Namespace をつなぐ

{rhsi} は、オープンソースの https://skupper.io[Skupper.io,window=_blank] を基盤とし、Namespace 間に暗号化されたアプリケーションレベルの接続を作成します。VPN、ファイアウォールルールの変更、パブリックネットワークへのサービス公開は不要です。

設定後、自分の Namespace にローカルの Service が作成され、リモートデータベースへ透過的に通信を転送します。

{blank}

データベースの環境は厳重に保護され、受信用ポートを公開していません。この状態を保つため、リンクはデータベース側 *から* *自分の Site に向けて* 開始します。自分の側で AccessGrant を作成するのは、データベースの Site に接続を許可し、双方向の通信リンクを確立するためです。データベース側に、攻撃され得る入口を開く必要はありません。

[#_what_you_will_do]

Service Interconnect の設定は 2 段階です。まず、環境を接続する安全なメッシュとして *ネットワークを確立* し、次にその上で *サービスを公開* します。ネットワークができれば、Listener と Connector を組み合わせるだけで新しいサービスを追加でき、ネットワークの変更は不要です。

この演習では、以下を行います。

*ネットワークの確立* — Namespace 間に安全なリンクを作成します。

[start=0]
. `shared-database` Namespace の *Site* は作成済みです _(設定済み)_
. 自分の Namespace に、`linkAccess` を有効にした *Site* を作成します
. データベースの Namespace が接続できるよう *AccessGrant* を生成します
. データベースの Namespace に *AccessToken* を作成し、リンクを確立します

*データベースサービスの公開* — リモートのデータベースをローカル (`{username}-devspaces`) で利用できるようにします。

[start=4]
. Skupper ネットワークと PostgreSQL のポート `5432` をつなぐ *Connector* は作成済みです _(設定済み)_
. リモートデータベースをローカルの Service として公開する *Listener* を作成します

[#_step_3_create_an_accesstoken_in_the_database_namespace]
==== 手順 3: データベースの Namespace に AccessToken を作成する

`shared-database` Namespace に AccessToken を作成し、データベース側から自分の Namespace へのリンクを確立します。Token の名前は `token-{username}` にしてください。

Grant の情報を取得し、AccessToken を作成します。

{blank}

[.copypaste]
****
URL=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.url}')
CODE=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.code}')
CA=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.ca}' | sed 's/^/    /')

cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-{username}
  namespace: shared-database
spec:
  url: "${URL}"
  code: "${CODE}"
  ca: |
${CA}
EOF
****

少し待つと、`shared-database` に *Link* リソースが自動作成されます。確認します。

{blank}

[.copypaste]
****

****

[#_expose_the_database_service]
=== データベースサービスを公開する

ネットワークができ、自分とデータベースの Namespace が暗号化されたリンクで接続されました。ただし、それだけではデータベースにアクセスできません。Service Interconnect に、*どのサービス* を自分の Namespace に公開するかを指定する必要があります。

ここで Listener と Connector を使用します。手順 0 で確認したように、データベース側の Connector は設定済みです。対応する Listener を自分の側に作成します。

{empty} +

[#_step_4_create_a_listener_to_expose_the_database_locally]
==== 手順 4: データベースをローカルに公開する Listener を作成する

Listener は、自分の Namespace にローカルの Service を作成し、暗号化されたリンク経由でリモートの PostgreSQL に通信を転送します。

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: postgres-listener
  namespace: {username}-devspaces
spec:
  routingKey: postgres
  host: postgres
  port: 5432
EOF
****

IMPORTANT: `routingKey` は、`shared-database` Namespace の Connector の設定と一致させてください。プラットフォームチームは `postgres` に設定しています。

Listener の準備ができたことを確認します。

{blank}

[.copypaste]
****
oc get listener postgres-listener -n {username}-devspaces
****

以下のような出力が表示されます。

* *サービスの公開* — Listener を作成し、ネットワーク経由でリモートのデータベースをローカルから利用できるようにしました。

確立したリンクは継続して使えます。次の演習で、保険申込の取り込み、データベースへの保存、PDF 保険証券の生成という一連のフローを実装する際に使用します。

[#_beyond_this_exercise_service_interconnect_at_scale]
=== 発展: 大規模な Service Interconnect

このラボでは、仕組みを理解するために同じクラスタ内の 2 つの Namespace を接続しました。実際には、同じ安全なメッシュを通じ、複数のクラスタ、地域、クラウドにまたがるサービスをつなぐ際に、Service Interconnect の強みが発揮されます。

複数地域に店舗を持ち、AI サービスを運用する小売企業を考えます。エッジ拠点は学習データを収集し、ローカルのモデルで推論します。冗長化したオンプレミスのデータセンターが新しい AI / ML モデルを学習し、更新版を店舗へ配布します。地域ハブが近隣のエッジの通信を集約して中核へ転送します。

ここでも、学んだ 2 段階の構成を使います。Site とリンクでネットワークを形成し、Listener と Connector で両端のサービスを公開します。1 クラスタ内の 2 つの Namespace から、複数の地域、ハブ、データセンターへ規模が変わっても、基本的な構成要素は同じです。
