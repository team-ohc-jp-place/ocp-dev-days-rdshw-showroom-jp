= Section 6: Stateless EJB から CDI へ (`ClaimService`)
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

[#_goal]
== 目標

Developer Lightspeed で、`ClaimService` を `@Stateless` EJB から、Quarkus 向けの `@ApplicationScoped` CDI Bean と `@Transactional` に移行します。

* Get Solution と MTA Resolution Details を使います
* 必要に応じてエージェントの追加支援で、関連するビルドや設定の問題に対応します

Enterprise JavaBeans (EJB) は、EAP で業務ロジックやコンテナ管理のトランザクションを扱う一般的な方法でしたが、Quarkus ではサポートされません。**parasol-insurance-eap** の `com.parasol.ejb.ClaimService` は、JPA の `EntityManager` で請求を一覧・検索する **ローカルの `@Stateless` セッション Bean** で、リモート EJB ではありません。HTTP はすでに JAX-RS 層の `ClaimsResource` が提供しているため、ここでは **サービス Bean 自体** をモダナイズします。

`ClaimService` を `@Stateless` から `@ApplicationScoped` + `@Transactional` に変え、トランザクション境界と CDI 注入を Quarkus の方式に合わせます。

[#_the_paradigm_shift_container_managed_ejb_to_cdi]
== コンテナ管理の EJB から CDI への変化

EAP の `@Stateless` は Bean のプール、コンテナ管理のトランザクション、`@EJB` / JNDI による接続を提供していました。EJB コンテナのない Quarkus では以下を使用します。

* Bean のライフサイクルには **`@ApplicationScoped`** または他の CDI スコープ
* `@Stateless` が暗黙に提供したトランザクション境界には **`@Transactional`** (Jakarta Transactions / Quarkus)
* 依存先の注入には `@EJB` の代わりに **`@Inject`** / CDI

対象はサービス層です。リモートインターフェースや RMI を REST に書き換える演習ではありません。`ClaimService` に `@Remote` はなく、JAX-RS から同一プロセス内で呼び出しています。

[#_benefits_of_going_cloud_native]
== クラウドネイティブ化の利点

* **簡単なプログラミングモデル:** EJB のライフサイクルを取り除き、通常の CDI Bean を使います。
* **明示的なトランザクション:** `@Transactional` で、コード上に境界を示します。
* **フレームワークとの整合:** 移行後の Parasol が使う Quarkus / CDI / Hibernate のパターンに揃えます。

[#_exercise_1_review_analysis_for_claimservice]
== 演習 1: ClaimService の分析を確認する

. Analysis パネルで `ClaimService` を検索します。開始前に **Agent Mode** が **On** であることを確認します。
+
image::module-05-mta-dls/05-06-dls-01.jpg[Agent Mode を有効にした ClaimService の解析,link=self,window=blank,title="エージェントモード"]

以下の指摘を確認します。ルールセットのバージョンにより文言は異なる場合があります。

* Quarkus は `@Stateless` をサポートしません。
  EJB の代わりに CDI を使用します。`@Stateless` を `@ApplicationScoped` などの CDI スコープに置き換えます。
* コンテナ管理のトランザクションを明示的に置き換えます。
  Stateless Session Bean は既定でコンテナ管理のトランザクションに参加します。Quarkus では Bean または業務メソッドに `@Transactional` を付け、請求の問い合わせをトランザクション内で実行します。
* `javax.ejb` のインポートはサポートされません。
  `javax.ejb.Stateless` を削除し、`jakarta.enterprise.context.ApplicationScoped`、必要なら `jakarta.transaction.Transactional` を使います。
* `javax` パッケージは `jakarta` に置き換わっています。
  解析の指摘に従い、永続化関連のインポートを更新します。例: `javax.persistence.*` → `jakarta.persistence.*`

[#_exercise_3_continue_with_agent_assisted_fixes]
== 演習 3: エージェントの支援で修正を続ける

. **Agent Mode** が有効だと、`pom.xml` の Quarkus 依存関係、永続化設定、他の依存先なども修正する場合があります。各提案を確認し、必要に応じて **Accept**、**Reject**、**Apply All** / **Stop** を選択します。
+
image::module-05-mta-dls/05-06-dls-04.jpg[エージェントによる pom.xml と関連箇所の追加修正,link=self,window=blank,title="エージェントによる追加修正"]

. エージェントは、修正の生成、追加変更の特定、ユーザーによる承認・拒否、IDE の診断取得、必要に応じた追加修正、というループで動作します。
+
image::module-05-mta-dls/05-06-dls-05.jpg[エージェントの流れ — 修正生成と診断および承認・拒否,link=self,window=blank,title="エージェントの処理の流れ"]
+
`ClaimService` を例に確認します。
+
* **修正の生成 (LLM)** — 「`@Stateless` を CDI スコープに置き換える」などの指摘を基に、アノテーション、インポート、`ClaimService.java` の呼び出し箇所を修正する最初のパッチを提案します。
* **追加変更の特定 (LLM)** — 1 つの変更が他にも影響します。`@Stateless` の除去後、`@PersistenceContext` → `@Inject`、`javax.*` → `jakarta.*`、EJB の接続を想定する `ClaimsResource` なども変更する場合があります。
* **承認・拒否 (あなた)** — 正しければ受け入れ、変更が過剰なら拒否し、必要ならエディタで確認します。ユーザーの選択なしに恒久的に適用されることはありません。
* **ツールからの診断 (IDE)** — 変更後、言語サーバーのエラー、未解決の型、Maven 座標の不備、Quarkus 拡張の欠落などを確認します。元の MTA の指摘にない不足にも気付けます。
* **追加修正の判断 (あなた + LLM)** — `pom.xml` の `quarkus-hibernate-orm` やデータソースの `application.properties` がないなどの診断が残ると、続行を尋ねます。**Yes** で次のパッチを生成し、**No** / **Stop** で終了します。
* **繰り返し** — 修正によって新しい診断が出る場合もあり、必要な状態になるか、ユーザーが止めるまで繰り返します。
+
**MTA による問題発見 → LLM の修正提案 → あなたの承認 → IDE 診断で次の問題を発見 → 必要なら再修正** という流れです。EJB → CDI などの波及に対応できるのが Agent Mode の利点ですが、各差分の確認も必要です。

エージェントは、修正後に生じる問題にも対処します。
例えば `EmailIntakeMDB` を Reactive Messaging に、`ClaimService` を CDI に変更した後、`pom.xml`、永続化設定、他の依存先も調整する場合があります。文脈と変更の影響を理解し、LSP サーバーやビルド・コンパイルツールなどを使用します。

新たな問題を見つけるたびに、続けるか確認します。ユーザーはいつでも終了できます。

[IMPORTANT]
====
いくつかの修正を試してください。続けたくない場合は **No** を選べます。提案の承認・拒否も、内容を確認して判断してください。
====
