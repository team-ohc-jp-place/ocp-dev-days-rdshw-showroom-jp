= Section 5: 監査ログライブラリのカスタムルール
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

[#_goal]
== 目標

独自ライブラリに MTA のカスタムルールが必要な理由を学びます。

* `parasol-insurance-eap` に付属する監査ログ用ルールを確認する
* MTA の分析プロファイルに追加する
* 分析を実行し、標準の Quarkus ルールでは検出できない問題を確認する

標準の Quarkus 向け移行ルールなどは、Java EE、Jakarta、一般的なオープンソースのフレームワークを扱いますが、Parasol 内部の `audit-logging-library` は認識しません。カスタムルールがないと、EJB や MDB が移行されても、古い監査 API が壊れたまま残り、保険業務のコンプライアンス上のリスクになります。

このセクションでは、プラットフォームやアーキテクチャのチームが一度作成し、依存するすべてのアプリケーションで再利用する、重要な移行知識としてカスタムルールを扱います。

[#_why_parasol_needs_custom_rules]
== Parasol にカスタムルールが必要な理由

Parasol Insurance は、プロジェクト内のローカル Maven リポジトリに配置された、共通の企業用ライブラリ `com.enterprise:audit-logging-library` に依存しています。

* **v1 (`1.0.0`)** — ファイルシステム中心の同期監査ログです。`AuditEvent` のビルダー、`FileSystemAuditLogger`、`logSuccess` / `logFailure` などの簡易メソッドを使います。
* **v2 (`2.0.0`)** — ストリーミング中心の API です。`StreamableAuditLogger`、record 形式の `AuditEvent`、ノンブロッキングの `logEventAsync` を使います。

JAR と POM は `lib/repository/` にあり、`pom.xml` が `project-local` ファイルリポジトリ経由で **v1** に依存しています。Maven Central にも、公開の Quarkus ルールにも存在しない、典型的な独自依存関係です。

[cols="2,2"]
|===
| v1 (現在) | v2 (移行先)

| 同期のファイルベースログ
| 非同期 / ストリーミングのログ

| `AuditEvent.builder()` パターン
| `AuditEvent` の直接生成 (record 形式の API)

| `FileSystemAuditLogger`
| `StreamableAuditLogger`

| `logEvent(...)`, `logSuccess(...)`, `logFailure(...)`
| 完全な `AuditEvent` を使い、`logEventAsync(...)` を優先
|===

[#_exercise_1_explore_the_custom_rules]
== 演習 1: カスタムルールを確認する

xref:module-05/module-05-logging.adoc[logging.yaml] を開き、内容を **ダウンロード** または **コピー** して、Dev Spaces の `parasol-insurance-eap/rules/logging.yaml` に保存します。`rules/` がなければ作成します。

`logging.yaml` の `ruleID`、`when:`、`message:` を確認します。解析結果として Analysis パネルに表示される内容です。`audit-logging-0001` から `audit-logging-0005` の **5 つ** のルールがあります。

[#_what_each_rule_detects]
=== 各ルールの検出対象

[cols="1,3,2"]
|===
| ルール ID | 検出対象 | 主な移行操作

| `audit-logging-0001`
| **1.x** の `com.enterprise:audit-logging-library` への Maven 依存関係
| `2.0.0` へ更新し、v2 が要求する Java バージョンにも合わせます

| `audit-logging-0002`
| `AuditEvent.builder` の呼び出し
| ビルダーを `AuditEvent` の直接生成に置き換えます

| `audit-logging-0003`
| `FileSystemAuditLogger` への参照
| ストリーミング / TCP 型の監査出力に対応する `StreamableAuditLogger` に切り替えます

| `audit-logging-0004`
| 監査ロガー型の同期 `logEvent(...)`
| ノンブロッキングの `logEventAsync(...)` を優先します

| `audit-logging-0005`
| 従来の `logSuccess` / `logFailure` 簡易メソッド
| 完全な `AuditEvent` を作成し、非同期で記録します
|===

TIP: カスタムルールは、公開ルールと同じ MTA ルール言語 (`java.dependency`、`java.referenced`、カテゴリ、工数、ラベル) を使います。違いは **管理主体** であり、Parasol 独自ライブラリの仕様を表しています。

`pom.xml` で、`audit-logging-library` の `1.0.0` への依存と、`lib/repository` を指す `project-local` リポジトリを確認します。これが `audit-logging-0001` の検出箇所です。

[#_exercise_2_attach_the_custom_rules_to_an_mta_profile]
== 演習 2: MTA プロファイルにカスタムルールを追加する

MTA 拡張機能には、解析にカスタムルールを追加する設定もあります。`quarkus-profile` に追加しましょう。

. MTA Analysis View で **歯車** アイコン (1) をクリックし、**Select Profile** の **Edit in Profile Manager** (2) を選択します。
+
image::module-05-mta-dls/05-05-dls-01.jpg[Get Ready to Analyze から Profile Manager を開く,link=self,window=blank,title="Edit in Profile Manager"]

. `quarkus-profile` にカスタムルールを追加します

. **Profile Settings** で、ワークショップと同じ移行先 (Quarkus / `quarkus-profile` と同じ系統) を選択します。このリポジトリのカスタムルールは Quarkus 3 系を対象としています。

. **Custom Rules** の **Upload Custom Rules...** で、保存した xref:module-05/module-05-logging.adoc[`logging.yaml`] をアップロードします。`logging.yaml` があるプロジェクトの `rules/` ディレクトリを指定しても構いません。
+
image::module-05-mta-dls/05-05-dls-02.jpg[Profile Settings でカスタムルールをアップロード,link=self,window=blank,title="Custom Rules"]

. プロファイルを有効にし、次の分析に使用します。

IMPORTANT: カスタムルールのパスやアップロードなしで `quarkus-profile` を実行すると、Java EE → Quarkus の指摘は表示されますが、監査ライブラリの問題は **検出されません**。標準ルールとカスタムルールは相互に補完します。

[#_exercise_3_run_analysis_and_inspect_custom_findings]
== 演習 3: 分析を実行してカスタムルールの結果を確認する

. 分析の準備ができました。先ほどと同じ `quarkus-profile` が有効なので、Analysis パネルで再度分析を実行します。

. **audit** / **`Audit`** に関する指摘を検索します。展開し、`logging.yaml` のルール ID と対応付けられるか確認します。少なくとも、`pom.xml` の `audit-logging-library` **1.0.0** への **依存関係** の指摘 (`audit-logging-0001`) があるはずです。

. `FileSystemAuditLogger` の置き換えなどの指摘で **AI** を開き、**Get solution** または **Get solution for N incidents** を選択します。
+
image::module-05-mta-dls/05-05-dls-03.jpg[監査ログの指摘と Get Solution,link=self,window=blank,title="解決策の取得"]

. **MTA Resolution Details** のパッチを確認します。`FileSystemAuditLogger` → `StreamableAuditLogger` などを確認し、**Review in Editor**、**Reject**、**Accept** を選びます。
+
image::module-05-mta-dls/05-05-dls-04.jpg[ClaimsResource のパッチの確認と承認,link=self,window=blank,title="Accept patch"]

. Analysis パネルで **`ClaimsResource`** を検索し、**Group by: Files** にします。**AI** からファイル全体の修正を依頼します。`AuditEvent.builder`、`logEvent`、`logSuccess` / `logFailure` などで `audit-logging-0002` ～ `0005` が検出されます。
+
image::module-05-mta-dls/05-05-dls-05.jpg[ClaimsResource のファイル単位の集約と Get Solution,link=self,window=blank,title="ClaimsResource AI"]

. 追加のパッチを確認します。例えば `logSuccess(...)` は、完全な `AuditEvent` の生成と通常は `logEventAsync` に置き換わります。差分を理解してから受け入れるか判断します。
+
image::module-05-mta-dls/05-05-dls-06.jpg[AuditEvent の移行パッチの確認,link=self,window=blank,title="AuditEvent patch"]

NOTE: 指摘の **message** をよく読んでください。「2.0.0 に更新」「`logEventAsync` を使用」など、人 *と* Developer Lightspeed の両方に意図が伝わるよう書かれています。モデルが Parasol の規約を推測する必要がありません。独自ライブラリの更新では、バージョン番号以外に Java や API の変更もあり得るため、差分を確認してください。

[#_what_we_learnt]
== 学んだこと

* **標準ルールの不足:** 公開の Quarkus / Java EE ルールは、`audit-logging-library` などの独自ライブラリを認識しません。
* **カスタムルールの構造:** `logging.yaml` の `when:` と、具体的な操作を示す `message:` を MTA と Developer Lightspeed が使います。
* **5 つの移行分野:** 依存関係の更新、イベントの生成、ロガー実装、同期から非同期への移行、簡易メソッドの除去です。
* **プロファイルとの接続:** 有効なプロファイルに `rules/` のパスを指定した場合だけ、カスタムルールが適用されます。
* **アプリケーション群での再利用:** 同じ `rules/` を、監査ライブラリに依存するすべての Parasol サービスで共有し、繰り返し分析できます。

[#_verify]
== 確認

. `parasol-insurance-eap` に `rules/` があり、その中に `logging.yaml` があることを確認します。必要なら、このガイドから取得してください。

. 5 つの `audit-logging-****` ルールのうち、少なくとも 3 つの検出内容を説明できます。

. カスタムの `rules/` パスを持つ MTA プロファイルを設定し、分析を実行しました。

. `pom.xml` の v1 依存関係に対する `audit-logging-0001` の指摘を特定できます。
